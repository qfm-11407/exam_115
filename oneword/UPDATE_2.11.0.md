# OneWord 2.11.0：縮短多人上傳的共用鎖

## 這次真實測試發現了什麼

2026-10-30 的工具報告顯示：30 個頁面中 28 名學生已加入，按送出的時間差為 16 毫秒；209 次送出程序中有 184 次收到本程式的共用鎖逾時訊息。監看截止時 16 人確認成功，稍後圖片核對讀到 17 張，測試未通過。

這是實際 GAS／Drive 測試，不是先前的本機模擬。流程演練沒有呼叫 AI；瓶頸在每次上傳及判讀狀態變更，都要在同一把鎖內讀寫整份 Drive 房間檔。舊版報告也有最後取樣時間差，不能把 16 與 17 的差異當作圖片損毀。

## 修正

- 活動中的房間狀態改存 GAS Script Properties，使用兩組分段資料及最後提交的索引。清空快取後仍從持久化資料復原，不會只靠 CacheService。
- 每段是最多 8000 位元組的 ASCII 編碼，兩組資料皆受大小上限約束。新資料未完整提交時仍讀取上一次已提交版本，避免儲存中斷後退回過期的 Drive 備份。
- 開題、收卷、公布、結束及切換房間時，備份至原 Drive 房間檔。結束及切換後釋放不再活動的狀態，避免多場歷史資料持續占用 Script Properties。
- PNG 圖片仍直接保存在原本的私人 Drive 題目資料夾；圖片及 AI 呼叫均不持有共用鎖。
- 每位學生先記錄獨立的伺服器收件憑證，再取得房間鎖。已在期限內收到的原圖可以跨截止重試；新圖、撤銷的身分及真正首次逾期送出仍拒收。未完成存圖的收件紀錄會阻止自動公布／換題；長時間未完成時暫停，等學生補送或教師處理。
- 上傳進行時優先接收圖片，暫緩新增判讀工作，以免判讀工作與收卷反覆爭鎖。現有已執行的 AI 請求不會取消。
- 測試工具更新為 v1.2.0，最後重新觀察狀態，以圖片完整核對作為保存證據，避免圖片核對數高於保存數的取樣矛盾。

Google 官方建議減少服務呼叫及使用批次操作；PropertiesService 也有每值及總儲存額度，本版採分段及活動房間釋放管理：

- https://developers.google.com/apps-script/guides/support/best-practices
- https://developers.google.com/apps-script/guides/services/quotas

## 更新步驟

1. 將新 `github-upload/` 的內容覆蓋 GitHub 的 `oneword/`。
2. 原 GAS 專案的 `Code.gs`、`Student` HTML 覆蓋為 `gas/Code.gs`、`gas/Student.html`。
3. 原部署選「部署 → 管理部署作業 → 編輯 → 新版本 → 部署」。不要重跑 setup_，也不要改原部署網址。
4. 教師與學生重新開啟頁面，確認「網頁 v2.11.0 · GAS 2.11.0」。
5. 若之前的壓測房間 F242F1 尚未結束，先在教師端結束該房間；前次報告顯示自動結束失敗。
6. 本機用本版 `scripts/gas-ui-loadtest.mjs` 覆蓋測試資料夾的同名檔，再執行 `TEST_GAS_30.cmd`。工具應顯示「測試工具版本：1.2.0」及「GAS 後端版本：2.11.0」。

此更新不需重新初始化或重新設定 API 金鑰。若未來要回退舊版 GAS，必須先結束活動測驗、完成 Drive 備份；舊程式不認識新版活動狀態儲存。

## 驗證的範圍

以實際後端程式配合服務替身計數，一題 28 人繳交及 28 次判讀，原版會讀取 112 次、重寫 112 次 Drive 房間狀態檔；本版讀取 0 次、重寫 1 次（收卷備份）。兩版都保存 28 張 PNG 並完成 28 份判讀。這是服務操作次數，不是上傳秒數，也不是新的真實 GAS 壓測成績。

回歸測試涵蓋快取遺失、分段／索引寫入中斷、備份失敗後重試、狀態大小、歷史房間釋放、期限內已收件但鎖逾時、截止後補送、身分撤銷、圖片不變，以及自動流程暫停及恢復。

必須重新執行真實 28 人測試，才能確認本次部署的成功率與耗時；本次尚無新版真實測試成績。即使全數成功，單台電腦的 30 個頁面仍不能完全代表 28 台平板與校內 Wi-Fi。流程演練的耗時也不能視為正式 AI 評分時間。
